# 失败场景处理

Phase 3 验证阶段可能遇到的失败场景及应对方式。

## 场景 1: Demo 开发失败

**原因**：技术难度超出预期 / 依赖环境不可用

**处理方式**：
1. 降级方案：用静态页面 + 假交互代替核心流程演示
2. 如有设计类 skill 可用（Pencil MCP、frontend-design 等），生成高保真原型图替代
3. 明确告知用户当前状态和降级原因，调整预期

## 场景 2: 用户中途改变需求

**处理方式**：
1. 评估变更范围：
   - 小变更（UI/文案） → 在 Phase 3 Iterate 中直接处理
   - 中变更（功能调整） → 回到 Phase 3 Build 重新开发
   - 大变更（核心逻辑改变） → 回到 Phase 1 重新发现，更新 requirement-assessment.md
2. 明确告知用户变更影响范围
3. 如有 product-brief.md，对照变更是否超出原始范围

## 场景 3: 用户没有部署条件

**原因**：无 GitHub/Vercel 账号，或公司网络限制

**处理方式**：
1. 本地运行 + 截图方式替代在线部署
2. 引导用户注册所需账号（提供链接）
3. 截图存入 `prototype/screenshots/` 作为验证证据

## 场景 4: 竞品调研结果不理想

**原因**：搜索结果不相关 / 找不到直接竞品

**处理方式**：
1. 扩大搜索范围：从直接竞品扩展到间接替代方案（用户现在用什么方式解决这个问题）
2. 如实告知用户搜索结果有限，标注哪些信息待校验
3. 建议用户补充自己了解的竞品信息
