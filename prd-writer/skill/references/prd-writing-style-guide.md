# PRD 写作风格指南

> 基于 23 篇 PRD（共 ~97,000 字）的量化分析提炼，覆盖共享支付赛道（14篇）和碰一下赛道（9篇）。

---

## 一、核心风格特征（5 条）

### 1. 零情态直陈式
不用"应该""必须""务必"等主观情态词，直接陈述系统行为或用户动作。需求即事实，不需要语气修饰。

- ✅ "设备端收到普通支付28码，判断链支付转会员后，上报会员服务端"
- ✅ "仅创建家长可关闭零花钱"
- ❌ "设备端应该在收到28码后上报服务端"
- ❌ "建议创建家长来关闭零花钱"

量化依据：23篇中"应该"出现3次，"必须"出现9次，"务必"出现0次。主要通过"支持X"（~370+次）和"需要X"（~265+次）表达需求。

### 2. "如…则…"条件主导
条件判断统一使用"如"，不用"如果""若"。形成"如X，则Y"的固定句式。

- ✅ "如零花钱余额为0，不拦截销户"
- ✅ "如超出上限，进入不可碰状态"
- ❌ "如果零花钱余额为0的话…"
- ❌ "若余额为零则不拦截"

量化依据："如"作条件词出现~150+次，"如果"仅~23次，"若"仅~5次。

### 3. 否定边界式需求定义
用"不做X""不支持X""仅X""本期不X"明确划定需求边界，而非仅描述要做什么。

- ✅ "不出退挽""本期不做""仅针对台式设备N5D"
- ✅ "不做视频内容""不做FAQ折叠模块""不做个性化内容推荐"

量化依据："不做/不支持/不涉及"合计~45+次，"仅"出现~170+次，"本期不做"~16次。

### 4. 表格驱动 + 散文收窄
结构化数据一律用表格（需求列表、人员保障、埋点、优先级、数据分析），散文仅用于背景叙述和设计决策解释。表格占全文内容组织约50%。

量化依据：23篇合计~1,000+表格行。核心表格模式：
- 需求描述表（需求点 | 需求说明）：出现在~18篇
- 人员保障表（干系域 | 接口人 | 技术 | 质量）：出现在~20篇
- 优先级矩阵（P0/P1色标）：出现在~16篇

### 5. 红色标注系统
#DF2A3F 红色字体是"注意力锚点"的专用色：标注待确认问题、关键数据、风险提示、行动项。不滥用，仅用于必须引起读者注意的内容。

量化依据：红色文字出现~110+次，场景分布：
- 待确认/未定事项：~40%
- 关键数据/指标：~30%
- 风险/警告：~20%
- 行动项/负责人标注：~10%

## 三、可操作的模仿规则

### 规则 1：需求表达三板斧
- **肯定能力**："支持X"
- **义务要求**："需要X" / "需X"
- **否定边界**："不做X" / "不支持X" / "仅X"

不使用"应该""务必""确保"等情态修饰。如果一个需求不确定，用"待X"标记而非"可能需要"。

### 规则 2：条件句统一用"如"
所有条件判断统一用"如X，（则）Y"格式。不用"如果""若""假设"。时序条件用"X时/后，Y"。

### 规则 3：主动语态 + 明确主语
93%以上使用主动语态。主语优先顺序：系统/服务名 > 用户 > 产品。被动语态仅在描述用户被动遭遇时使用（"被拦截""被扣款"）。

### 规则 4：句长控制在25-35字
超过40字的句子拆分。表格单元格内控制在15字以内。背景段落可适当放宽到50字。

### 规则 5：表格优先于散文
遇到以下内容必须用表格：
- 多个同类需求点 → 需求点 | 需求说明
- 人员分工 → 干系域 | 接口人 | 技术
- 优先级矩阵 → 序号 | 需求 | 干系域 | 优先级
- 数据指标 → 指标 | 定义 | 口径 | 目标值
- 埋点清单 → 事件 | 触发时机 | 关键参数

散文仅用于：背景叙述、设计决策解释、方案比选分析。

### 规则 6：红色标注系统
仅以下场景使用 #DF2A3F 红色：
- 待确认事项（"待业务确认"）
- 关键数据（"日均2.5w笔支付失败"）
- 风险/阻塞（"可能导致资损"）
- 行动项标记

不要用红色做普通强调，普通强调用**加粗**。

### 规则 7：不确定性分级标记
| 确定性 | 标记方式 | 示例 |
|--------|---------|------|
| 已确定 | 直接陈述 | "支持组合支付" |
| 需确认 | 红色+待X | "<font color=#DF2A3F>待技术确认</font>" |
| 暂推迟 | 灰色文字 | "<font color=#8A8F8D>非本期</font>" |
| 已放弃 | ~~删除线~~ | "~~涉及多端改造，成本较高~~" |

### 规则 8：标题用全角竖线分隔领域
PRD标题格式：`{领域}｜{需求名称}`。如"支付成功率｜设备无网支付方案""用户教育｜碰一下安全感教育页"。

### 规则 9：代码和技术参数的处理
- 技术标识符（接口名、字段名、枚举值）直接写在正文中，不必包裹代码块
- 仅在需要展示完整接口定义或配置结构时使用代码块
- 用 `TypeScript interface` 格式描述配置字段结构

### 规则 10：图片标注规范
每个需要补图的位置必须标注类型：
- ⚠️ Demo页面截图（标注截哪个状态/区域）
- ⚠️ 多状态对比图（需从Demo截图二次加工）
- ⚠️ 流程示意图（需设计师/产品自制）
- ⚠️ 数据表格截图（标注数据来源）

## 四、4 种描述模式：格式规范与风格示例

根据模块类型选择对应的描述模式。一个 PRD 内通常混合使用多种模式。以下从真实 PRD 中摘取（已脱敏），展示每种模式的格式特征和标准写法。

---

### 模式 A：H5 页面 / 组件描述

适用于：页面结构、UI 组件、筛选器、浮层等

**格式特征**：
- 组件名做小标题，后接缩进 bullet list 展开子功能
- 每个 bullet 是一个独立的功能点或规则，控制在 1-2 行
- 条件逻辑用嵌套 bullet 表达
- 准入条件单独成块，用编号列举

**示例（脱敏）**：

```
改善建议区
根据用户uid实时校验当前APP版本和系统版本：
* 非最新版（APP＜X.X.X，系统＜X.X）则显示「去升级」功能按钮
    * 点击直接跳转应用商店升级页、打开引导升级弹窗
* 满足最新版，则在该条后显示无需升级（具体设计以视觉稿为准）
* 两个版本号独立判断
* 如用户非目标系统或无法读取到系统版本，则不显示此条的按钮
```

**要点**：每个 bullet 是一个独立的功能点或规则，条件逻辑用嵌套 bullet 表达，视觉细节用"以设计稿为准"。

---

### 模式 B：弹窗 / 卡片变体描述

适用于：同一组件的多种状态或变体（有金额/无金额、不同用户身份等）

**格式特征**：
- 变体用编号区分（1. 有金额弹窗 / 2. 无金额弹窗）
- 每个变体内部用平行结构：主文案、副文案、行动点
- 行动点内区分主按钮和次按钮，分别描述点击后行为
- 动态内容用 #{变量名} 标记

**示例（脱敏）**：

```
1. 有金额弹窗：针对前置传入了金额的订单
    * 全局弹窗，交互遵循客户端现有规范
    * 主文案：本单支付享优惠，独立一行
    * 副文案：最高可减 #{动态金额} 元，数字部分红色放大加粗
    * 行动点：
        * 主按钮：继续付款，点击后推进支付流程
        * 文字：放弃，点击后视为用户主动关单
2. 无金额弹窗：无金额订单，统一使用模糊金额文案兜底
    * 全局弹窗，交互遵循客户端现有规范
    * 主文案：本单支付 可享笔笔立减优惠
    * 行动点：（同上）
```

**要点**：动态内容用 #{变量名} 标记，行动点区分主按钮和次按钮并分别描述点击后行为。

---

### 模式 C：复杂链路 / 流程描述

适用于：多步骤业务流程、支付链路、多端交互

**格式特征**：
- 按"正常链路 → 异常链路1 → 异常链路2 → 其他异常"分块
- 每个链路按角色视角展开（用户侧 / 设备侧 / 服务端）
- 时序条件用具体数值，可配置参数用括号标注
- 未定事项用"待讨论"标记，可附讨论点

**示例（脱敏）**：

```
正常链路
* 用户侧：唤端后进入准备页，确认token，等待服务端推送消息，
  收到后进入支付页，后续与标准流程一致
    * 准备页优化：最少停留时间300ms，loading状态优化
* 设备侧：
    * 感应成功后，保持待机页不变
    * 收到28码+uid，判断客户端版本，走到新链路，先按住28码不发
    * 从收码开始计时，如2s内收到商家小指令（2s时间可配）
        * 如商家发起普通支付，则链接复用，快速唤起支付
        * 如商家发起会员支付，则支付转会员

异常链路1-客户端非新版本
* 用户侧：客户端版本未支持，唤端后进入支付页，与标准流程一致
* 设备侧：收到28码，无uid（待讨论：是否约定标记），直接发出28码
```

**要点**：时序条件用具体数值，可配置参数用括号标注"（2s时间可配）"，未定事项用"待讨论"标记。

---

### 模式 D：数据指标 / 实验描述

适用于：指标定义、AB 实验设计、数据需求

**格式特征**：
- 指标按层级组织：北极星指标 → 过程指标 → 基础指标 → 分析指标
- 每个指标格式：指标名 + 公式定义 + 口径说明
- AB 实验用编号列举实验组，对比用 vs 连接
- 基础指标和分析指标用 bullet list 快速列举

**示例（脱敏）**：

```
1. 北极星指标：模拟体验拉新转化率
   口径：完成过至少一次模拟体验的用户中，在1天/7天/30天内
   完成至少1次目标行为的用户占比
   实验对比：同质用户在同一周期内，未曝光过模拟体验的转化率

2. 过程指标：功能打开率
   通过模拟体验后打开目标功能的用户数、占比

3. 基础指标
    * 入口曝光 pv uv
    * "去看看怎么用"点击率
    * 人均停留时长

4. 分析指标（用于转化率问题的拆解分析）
    * 体验开始率 = 开始模拟体验的用户数 / 进入页面的用户数
    * 体验完成率 = 成功完成模拟的用户数 / 开始模拟的用户数
    * 中途退出率 = 开始但未完成就退出的用户数 / 开始模拟的用户数
```

**要点**：指标分层为北极星 → 过程 → 基础 → 分析，每个指标用"口径"说明计算规则，分析指标用公式定义。

### 模式选择逻辑

Phase 1 推断时自动判断模块类型：
- 有 UI 界面/页面结构 → 模式 A
- 有同组件多变体（弹窗多状态、卡片多类型）→ 模式 B
- 有多步骤串联/多端交互/支付链路 → 模式 C
- 有指标定义/AB 实验 → 模式 D

## 五、两种PRD模板的风格差异

| 维度 | 共享支付赛道（技术PRD） | 碰一下/用户教育赛道（体验PRD） |
|------|----------------------|--------------------------|
| 标题 | 纯Markdown heading | 中文序号（一、1.1、3.2.1） |
| 需求表达 | 需求点+需求说明表格为主 | 组件名小标题+缩进bullet list为主 |
| 决策解释 | 方案选型对比表 | 仅在方案比选章节使用对比表+推荐结论 |
| 设计细节 | 较少视觉描述 | 不写具体视觉参数，用"以设计稿为准" |
| 散文比例 | ~40% | ~60% |
| 表格比例 | ~60% | ~40% |
| 代码块 | 极少 | TypeScript interface描述配置 |
| 图片标注 | 直接嵌入截图 | ⚠️标注+说明图片类型 |

选择模板时，根据PRD受众和内容复杂度决定：
- 技术改造、链路治理、系统能力升级 → 共享支付赛道模板
- 用户界面、教育页面、体验优化 → 碰一下赛道模板
