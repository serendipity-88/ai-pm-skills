# T3: 竞品监控分析平台（论证路径）

## 测试目标

验证论证路径的深度调研能力，重点测试 Phase 1 的扩展调研模式。

## 用户输入

```
我想做一个竞品监控分析平台——自动抓取竞品的产品更新、定价变化、用户评价，生成周报给产品团队。这个项目需要立项，我要说服老板投入 2 个开发做 3 个月，帮我把调研做扎实。
```

## 预期行为

### 分流判断
- 应识别为**论证**路径（"需要立项""说服老板""调研做扎实"）
- 应走完整 Phase 1（深度模式）→ 2 → 3 → 4

### Phase 1a 问题定义
- **JTBD 转化**：应转化为 JTBD 句式，例如：
  - "当产品团队需要了解竞品动态时，想要自动获取竞品的产品更新、定价和用户评价，以便及时调整产品策略而不用人工逐个监控"
- **需求分类**：应标注为**痒点**（没有也行但有了更好——目前人工也能做，只是效率低）或**痛点**（取决于推断的紧迫程度）
- **7 维度评估**：
  - 应推断：痛点（人工监控效率低）、用户（产品团队）、场景（周期性竞品跟踪）
  - 应追问：监控哪些竞品、数据源有哪些、周报分发渠道、团队现在怎么做竞品跟踪

### Phase 1b 竞品调研（深度模式）
- 应搜索 **5+ 竞品**（论证模式扩展要求）
- 相关竞品可能包括：Crayon、Klue、Kompyte、Contify、SEMrush Market Explorer 等
- 每个竞品应有详细对比：
  - 它怎么解决同样的问题
  - 核心差异
  - 迁移/替代成本
- 应标注"待用户校验"的关键事实
- 应生成 `assets/research-findings.md`（内容比正常模式更详细）

### Phase 1c 调研摘要
- 应呈现完整调研结果，包括：
  - JTBD + 需求类型
  - 5+ 竞品的对比摘要
  - 核心差异点（我们方案独特在哪）
  - **风险提示**（论证模式应更详细）：
    - 技术风险：抓取竞品数据的合规性和稳定性
    - 市场风险：成熟竞品已存在，差异化空间
    - 资源风险：2 人 3 个月是否足够
- **HARD-GATE**：等待用户确认

### Phase 2
- 应基于深度调研结果设计方案
- 核心场景裁剪：≤3 个核心场景
- 范围边界应特别清晰（立项文档需要明确边界）
- 应生成 `assets/product-brief.md`
- **HARD-GATE**：展示产品简报，等待确认

### Phase 3
- 应检测已安装的相关 skill 并推荐
- Demo 应聚焦核心场景验证
- Iterate 微循环

### Phase 4
- 应调用 prd-writer
- 论证场景下 PRD 质量要求更高（因为要用于立项）

## 对照测试

裸跑 prompt：
```
帮我调研一下竞品监控分析平台这个方向，我想做一个自动抓取竞品产品更新、定价变化、用户评价并生成周报的工具。需要立项，要说服老板投入 2 个开发做 3 个月，帮我把调研做扎实，然后做个 Demo。
```

## 评估点

| 维度 | 检查项 |
|------|--------|
| 分流准确性 | 是否正确识别为论证路径 |
| 调研深度 | 竞品是否 ≥5 个、对比是否结构化 |
| 风险识别 | 是否识别技术/市场/资源风险 |
| JTBD 质量 | 是否从"做个平台"还原到用户场景 |
| 追问精准度 | 是否仅追问必要信息、不过度提问 |
| HARD-GATE | 两个关键门禁是否生效 |
| 立项适配 | Phase 2 范围边界是否足够清晰 |
| 端到端完整性 | Phase 1(深度)→2→3→4 是否完整 |
| PM 警戒线 | 是否避免了不必要的追问和输出 |
