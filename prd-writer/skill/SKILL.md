# PRD Writing Skill

## 定位

本 skill 用于**已有原型、Demo 或方案文档后**，反向生成结构化 PRD。

核心理念：**先做东西，再写文档**。先用 vibe coding 出 Demo、先画原型、先写方案，再用本 skill 将已有成果转化为结构化 PRD。

> **前提**：项目目录下需有方案文档、Demo 代码或设计稿。如只有模糊想法尚无材料，建议先走 ai-native-pd 工作流。
> 如果你刚用 ai-native-pd 做完 Demo，本 skill 会自动识别已有产出并加速流程。

## 触发前判断

在执行前，先判断：

1. **是否需要 UI 界面？** 涉及用户交互（页面、弹窗、按钮）→ 继续；纯后端 → 继续（简化 PRD）
2. **是否已有原型/Demo？** 有代码文件（.html/.vue/.tsx/.jsx/.py 等）→ 继续；需要 UI 但无任何代码或设计 → 建议先走 ai-native-pd 工作流

## 执行流程

```
Phase 1: 读取项目材料 → 推断 31 维度 → 写入 .prd-cache/dimensions.yaml → 输出项目理解摘要（用户确认）
         └→ 自动判断流程模式：轻量（#2=轻量 且 #3=轻量 且 #29≠多端 且 #25≠需要）或 完整
Phase 2: [完整模式] 2 轮交互确认（成功指标讨论 + 必问项）
         [轻量模式] 仅 Round 2 必问项（跳过成功指标讨论）
Phase 3: [完整模式] 读取骨架模板 → 按推断结果裁剪 → 输出框架（用户确认）
         [轻量模式] 跳过，直接进入 Phase 4
Phase 4: 填充完整内容（参考 references/ 中的写作规范和风格指南）
Phase 5: [完整模式] 用户看第一版 → subagent 规则验证 → 输出修改建议 → 用户确认后修改
         [轻量模式] 用户看第一版 → subagent 仅检查禁用表达和格式规范
```

## Phase 1: 自动推断维度

读取项目目录下所有材料，自动推断以下 31 个维度 + 图表衍生规则。**不需要询问用户，全部从材料推断**。

当项目主要材料为代码（无方案文档或方案文档简略）时：
- 可从代码推断的维度：#1 产品类型、#3 复杂度、#9 状态机、#19 流程、#20 交互规范、#29 链路复杂度 — 正常推断
- 代码中无法推断的维度：#8 背景深度、#10 用户调研、#11 客户原声、#14 版本深度、#26 范围排除 — 标记"待确认"，自动追加到 Phase 2 必问项
- 如项目含需求评估文档（如 requirement-assessment.md），作为补充材料辅助推断

### 1.1 产品形态维度（6 项）

| # | 维度 | 推断逻辑 |
|---|------|---------|
| 1 | 产品类型 | HTML→H5页面，小程序→小程序，API→后端服务 |
| 2 | 产品规模 | 单页面→轻量，多页面/多模块→中型，跨端→大型 |
| 3 | 产品复杂度 | ≤2 个功能模块→轻量；3-5 个模块→中型；≥6 个模块或存在跨模块数据流→复杂。模块 = 独立功能区域，有自己的入口或页面 |
| 4 | 合规要求 | 涉及支付/金融→需合规说明，纯展示→无 |
| 5 | 产品状态 | 有线上版本→迭代，全新→v1.0 |
| 6 | 用户角色与权限 | 多角色系统→需要角色权限矩阵，单角色→不需要 |

### 1.2 内容结构维度（10 项）

| # | 维度 | 推断逻辑 |
|---|------|---------|
| 7 | 文档格式 | 默认 HTML + Markdown 双版本 |
| 8 | 背景深度 | 全新赛道→需要行业背景，成熟功能迭代→简述即可 |
| 9 | 状态机 | ≥3 个互相可达的状态→需要状态机图（PlantUML stateDiagram）；2 个状态（开/关、有/无）→文字描述即可 |
| 10 | 用户调研表 | 有用户画像数据→纳入，无→跳过 |
| 11 | 客户原声 | 方案中引用了用户原话→纳入，无→跳过 |
| 12 | 视觉素材 | 有设计规范/截图→嵌入 PRD，无→文字描述 |
| 13 | 数据复杂度 | 多组数据对比→需要数据表格，单一数据→行内描述 |
| 14 | 版本深度 | v1.0→演进规划简述，v2.0+→需要版本对比 |
| 15 | 对比表格 | 有多方案比选→需要对比表+一句话决策，无→跳过 |
| 16 | 名词解释 | 有业务专有名词→需要术语表，通用概念→跳过 |

### 1.3 流程与交互维度（6 项）

| # | 维度 | 推断逻辑 |
|---|------|---------|
| 17 | 用户动线 | ≥2 个入口且导向不同页面/流程→需要动线图；多入口但汇聚到同一页面→文字列举入口即可 |
| 18 | 用户用例 | 多角色多场景→需要用例表，单一场景→不需要 |
| 19 | 业务流程图 | 满足任一→需要流程图：①≥3 个顺序步骤；②≥2 个参与角色/系统交互；③存在条件分支。均不满足→文字描述 |
| 20 | 交互规范 | 简单交互（单按钮→确认→完成）→行内一句话描述；复合交互（多状态切换/多步操作/条件分支/有异常降级）→完整 5 要素覆盖（默认状态、触发、行为、取消、降级） |
| 21 | 性能要求 | 有加载时间/帧率要求→纳入非功能性需求，无→跳过 |
| 22 | 兼容性 | 跨平台/跨浏览器→需要兼容性矩阵，单平台→跳过 |

### 1.4 工程与运营维度（6 项）

| # | 维度 | 推断逻辑 |
|---|------|---------|
| 23 | 埋点追踪 | 方案中提及数据度量→生成埋点清单，无→跳过 |
| 24 | 安全性 | 涉及用户数据/支付→需要安全说明，纯展示→跳过 |
| 25 | 灰度与回滚 | 有 AB 实验→需要实验设计，无→跳过 |
| 26 | 范围排除 | 明确不做的功能→列出排除项 |
| 27 | 依赖与待定 | 有外部依赖/未确认事项→列出待定问题表 |
| 28 | 验收标准 | 有明确可测试条件→纳入，否则跳过 |

### 1.5 补充推断维度（3 项）

| # | 维度 | 推断逻辑 |
|---|------|---------|
| 29 | 链路复杂度 | ≥2 个端参与交互（前端+后端+设备端等）→触发模式 C，需正常链路+异常分支描述；纯单端→不触发 |
| 30 | 风险等级 | 材料出现关键词：金额/支付/转账/退款/敏感数据/身份信息/实名/征信/合规/审计→触发"风险与应对"章节（四视角评估）；未命中→跳过 |
| 31 | 文档说明需求 | 迭代需求（v2.0+）→需要版本更新记录；名词解释由 #16 独立控制，位于需求概述章节 |

### 图表类型衍生规则（由上述推断结果自动确定）

| 触发条件 | 生成图表 |
|---------|---------|
| #29 链路复杂度=多端 | 时序图（PlantUML sequenceDiagram） |
| #9 状态机=≥3 状态 | 状态机图（PlantUML stateDiagram） |
| #19 业务流程图=需要 | 流程图（Mermaid flowchart） |
| #3 复杂度=复杂 且 ≥3 个系统/组件 | 架构图（Mermaid graph TB） |

> **注**：Demo 截图、多状态对比图等无法自动生成的图片，用 `📷 图片占位` 占位，详见 `references/image-placeholder-rules.md`。

### 1.6 干系人推断

**从产品需求推断，不是从代码推断**。每个角色必须说明"做什么"。

| 角色 | 推断条件 | 说明示例 |
|------|---------|---------|
| 前端 | 有用户界面 | H5页面开发：首屏、交互组件、动画、埋点上报 |
| 后端 | 有配置化需求/接口/数据存储 | 配置接口开发：页面内容按用户标签下发、埋点数据落库 |
| 客户端 | 需要 Native 能力（相机/NFC/推送） | 如无 Native 依赖则标注"纯 WebView 承载，无 Native 依赖" |
| 设计 | 有用户感知的 UI/UX/视觉 | 视觉定稿：配色、间距、图标确认，多状态视觉 |
| 数据 | 有 AB 实验/数据分析需求 | 实验分组、数据回收、效果分析 |

### 1.7 Phase 1 输出

推断完成后：

1. 将维度表写入 `prd/.prd-cache/v{版本号}/dimensions.yaml`（格式：`#N 维度名: 结果值`，31 行）
2. 读取 `templates/phase1-summary.md` 输出项目理解摘要给用户确认，同时写入 `prd/.prd-cache/v{版本号}/phase1-summary.md`

> `prd/.prd-cache/` 是所有过程文件的存储目录，Phase 间数据传递通过文件，不依赖对话上下文。

## Phase 2: 交互确认（最多 2 轮）

> **轻量模式**：跳过 Round 1，仅执行 Round 2 必问项。

### Round 1: 成功指标讨论（完整模式）

先基于材料**自主推断**成功标准，然后展示给用户讨论。

推断逻辑：
1. 从方案文档中提取目标描述
2. 区分**核心指标**（决定产品是否成功）和**过程观测指标**（理解用户行为，不作为效果评判）
3. 如涉及 AB 实验，明确实验组 vs 对照组的观测指标

指标分层体系：北极星指标 → 过程指标 → 基础指标 → 分析指标。数据表达使用 X%→Y%（+Zpt）格式，避免"显著提升"等模糊表达。

### Round 2: 必问项（一次性问完）

在成功指标确认后，**一次性**询问以下问题（如 Phase 1 已从材料获得明确答案，可跳过该问题）：

| # | 问题 | 为什么必须问 |
|---|------|-------------|
| 1 | 已知约束 | 技术限制、合规红线、资源瓶颈，无法从材料推断 |
| 2 | 配置化/运营需求 | 哪些内容需要运营侧可配置，影响接口设计 |
| 3 | AB 实验设计 | 分组策略、实验周期、核心观测，需要用户决策 |

> PRD 受众默认值见 `config.yaml` 中 `defaults.audience`。

Phase 2 交互完成后，将成功指标和必问项回答写入 `prd/.prd-cache/v{版本号}/phase2-decisions.md`。

### 灰色地带（按需决定，不询问用户）

| 维度 | 纳入条件 |
|------|---------|
| 异常与降级 | 有网络请求/外部依赖/复杂交互→纳入 |
| 演进规划 | 明确标注 v1.0→纳入后续版本展望 |
| 验收标准 | 多角色协作/复杂功能→纳入可测试条件 |

## Phase 3: 框架先行

> **轻量模式**：跳过本阶段，直接用最小骨架（概述 + 需求描述 + 干系人）进入 Phase 4。

**完整模式：必须先输出框架，等用户确认后再填充内容。**

读取 `prd/.prd-cache/v{版本号}/dimensions.yaml` 和 `templates/prd-skeleton.md`，根据维度推断结果裁剪章节（条件不满足的整段删除）。裁剪后的框架写入 `prd/.prd-cache/v{版本号}/phase3-framework.md`。输出框架需包含：

1. 裁剪后的章节标题列表（含每章预计涵盖的内容要点）
2. 对需要特殊处理的章节给出建议（如"这里建议用时序图""这里需要补截图"）
3. 需求优先级表（P0/P1/P2 分级）
4. 每个功能模块的描述方式（用自然语言说明，不暴露内部模式标签）
5. **图表风格确认**：如果图表衍生规则触发了任意图表，询问用户："本次 PRD 中的图表默认使用 Mermaid/PlantUML（语雀可编辑）。如需高保真视觉效果（如对外演示），可改用 Fireworks Tech Graph（SVG→PNG，不可在语雀编辑）。请确认图表风格偏好。"用户选择 Fireworks 时，Phase 4 写作阶段对应图表改用 Fireworks Tech Graph 生成，并参考 `references/chart-guide.md` 的"增强路径"章节。

### 模式选择逻辑（内部使用，不对用户暴露 A/B/C/D 标签）

| 内部标签 | 对用户展示为 | 触发条件 |
|---------|-------------|---------|
| 模式 A | 页面结构描述 | 有 UI 界面/页面结构 |
| 模式 B | 多状态变体描述 | 有同组件多变体 |
| 模式 C | 多端链路描述（含异常分支） | 有多步骤串联/多端交互 |
| 模式 D | 数据指标与实验描述 | 有指标定义/AB 实验 |

## Phase 4: 内容写作

读取 `prd/.prd-cache/v{版本号}/dimensions.yaml` 确认维度结果，然后**必须读取以下 reference 文件**作为写作规范。当主要材料为代码时，功能描述必须从**用户视角**撰写（"用户点击XX后看到YY"），不从实现视角撰写（"组件调用 handleClick 触发 setState"）。

- `references/writing-rules.md` — 基础写作规则、交互描述规范、数据格式、符号、术语
- `references/forbidden-patterns.md` — 禁用表达清单、不确定性分级标记
- `references/prd-writing-style-guide.md` — 量化风格规则、4 种描述模式详细格式与示例、模板差异
- `references/chart-guide.md` — 图表类型选择决策树、工具用法细节、PlantUML 写法规范、Fireworks 可选增强路径（仅在需要画图时加载）

## 产出物

所有产出写入项目目录下 `prd/`，过程文件存入 `prd/.prd-cache/`：

```
prd/
├── PRD_{项目名}_v1.0.md         ← 最终 PRD（项目名从 Phase 1 推断的产品名称提取）
├── PRD_{项目名}_v1.0.html       ← HTML 版本（如需要）
└── .prd-cache/
    └── v1.0/
        ├── dimensions.yaml      ← Phase 1 维度推断结果
        ├── phase1-summary.md    ← Phase 1 项目理解摘要（用户确认版）
        ├── phase2-decisions.md  ← Phase 2 成功指标 + 必问项回答
        ├── phase3-framework.md  ← Phase 3 PRD 框架（用户确认版）
        └── phase5-review.md     ← Phase 5 质量检查报告
```

项目名提取规则：从 README.md 或需求文档中提取产品/项目名称，取简短中文名或英文标识（2-8 字），如"团队知识库搜索"→`团队知识库搜索`，"支付成功率方案"→`支付成功率`。如无法提取，用目录名作为项目名。

每个 Phase 完成后立即写入对应文件。迭代时新建版本目录（`v1.1/`），不覆盖历史。

版本管理：重大变更 → 主版本 +1；功能调整 → 次版本 +1；文字修正 → 不升级。

语雀同步：Phase 5 完成后自动同步（`config.yaml` 中 `yuque.auto_sync`）。同步流程如下：

1. **统计代码块**：统计本地 PRD Markdown 中 ` ```mermaid ` 和 ` ```plantuml ` 代码块的数量
2. **生成 body**：将 Markdown 转为语雀 body，所有 Mermaid/PlantUML 代码块原样保留（语雀原生渲染，不得替换为文字描述或占位符）
3. **校验 body**：确认 body 中 mermaid/plantuml 代码块数量与源文件一致，如不一致则修复后重试
4. **上传**：调用语雀 API 写入文档
5. **回读校验**：用 API 读回语雀文档，确认代码块数量和渲染正常
6. **处理图片**：有截图素材→上传替换占位符；无素材→保留 `📷 **图片占位**：{类型} - {说明}` 格式（位置、操作字段必填）

**同步格式规则（硬性）**：
- Mermaid 和 PlantUML 代码块语雀原生渲染，同步时必须原样保留，不得替换为文字描述或占位符
- 仅图片类占位允许保留占位符，代码块类图表不允许占位
- 图片占位符统一使用 `📷 **图片占位**` 格式，不用 `⚠️`

## Phase 5: 规则验证

Phase 4 写完 PRD 后，**先交给用户看第一版**，然后启动 subagent 做规则合规检查。

### 流程

1. 输出 PRD 第一版给用户阅读
2. 同时启动一个 subagent，传入：
   - PRD 文件路径
   - `prd/.prd-cache/v{版本号}/dimensions.yaml`（用于条件化裁剪检查项）
   - `references/writing-rules.md`
   - `references/forbidden-patterns.md`
   - `references/prd-writing-style-guide.md`
   - 下方质量检查清单（subagent 根据维度结果跳过不适用的条目）
3. subagent 逐条对照规则，输出检查报告（pass/fail + 具体修改建议），写入 `prd/.prd-cache/v{版本号}/phase5-review.md`
4. 将报告展示给用户，用户确认哪些修改建议要执行
5. 按用户确认的建议修改 PRD

### 质量检查清单（subagent 根据 dimensions.yaml 条件化执行）

**始终检查：**
- [ ] 需求优先级是否清晰（P0/P1/P2）
- [ ] 干系人是否从产品需求推断，且说明了每个角色"做什么"
- [ ] 禁用表达是否已全部替换（参考 references/forbidden-patterns.md）
- [ ] 交互描述格式：按钮文案用「」、动态内容用 #{}、可配置项用（）标注
- [ ] 情态词使用：不用"务必""确保"，用"支持""需要""不做"

**条件检查（维度不满足则跳过）：**
- [ ] <!-- if: #26=有 --> 范围排除是否明确列出"不做什么"
- [ ] <!-- if: #20=复合交互 --> 每个可交互元素是否覆盖了：默认状态、触发、行为、取消、降级
- [ ] <!-- if: #29=多端 --> 复杂链路是否包含正常链路+异常链路分支
- [ ] <!-- if: #29=多端 --> 多端交互是否按角色视角（用户侧/设备侧/服务端）分别描述
- [ ] <!-- if: #23=需要 OR #25=需要 --> 数据表达是否使用标准格式（X%→Y%、+Zpt、公式定义+口径）
- [ ] <!-- if: #23=需要 OR #25=需要 --> 数据公式：有指标定义的地方是否给出公式（指标名 = 分子 / 分母）
- [ ] <!-- if: 图表衍生规则触发任一 --> 需要图表的地方是否已生成（Mermaid/PlantUML 代码）
