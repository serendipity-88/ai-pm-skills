> 记录从 idea 到 skill 的完整过程：动机、决策、用户反馈、方法论选择。

## 2026-05-01：项目初始化

**起点**：发现 deep-research skill 在三个安装目录（`.claude/skills/`、`.codefuse/engine/cc/skills/`、`.codefuse/fuse/skills/`）版本不同步。`.codefuse/engine/cc/` 有最新版（含 templates/、更新后的 SKILL.md），另外两个停在旧版。

**决策**：收拢到 `ai-skills/deep-research/` 项目目录作为唯一源，通过 `publish.sh` 同步。这是 round-0 的内容。

## 2026-05-02：发现 hv-analysis（横纵分析法）

**触发**：用户分享了 GitHub 仓库 `KKKKhazix/khazix-skills`，其中 hv-analysis skill 与 deep-research 同领域但各有优势。

**hv-analysis 核心亮点**：
- 双轴框架（纵轴历时 + 横轴共时 + 交汇洞察）——比四阶段流水线更直觉
- 写作风格指导极细致（叙事驱动、反 AI 味、敢下判断）
- PDF 产出链路完整
- 竞品场景分 A/B/C 三种处理
- schema.json 结构化数据定义

**hv-analysis 相对 deep-research 的不足**：
- 没有 takeaway/决策指引层
- 没有可信度校准
- 没有交叉验证机制
- 信息收集方法欠指定（只说"3 个并行子 Agent"）

## 2026-05-03：用户核心洞察——深度调研是过程不是产品

**用户原话**：
> "作为各种行业的产品经理，想要了解一个新的赛道，或者在一个既有赛道里，想要去创新一个产品功能，需要大量的深度调研。它不仅仅是一个功能，而是对整个行业上下游现有的一些共识、认知、技术能力到竞品的设计，要进行全面的了解。而了解和产出这样一份深度调研分析并不是结果，仍然是过程。它最重要、帮助的是这个产品经理能够完成前期的需求分析。以最后帮助他通过后续的流程，产出最终的产品设计。切记不能本末倒置，过于追求深度调研的形式，而忽略了它要解决的问题。"

**这句话改变了一切**：
1. 产出不是研究报告，是决策依据
2. 信息密度比信息量重要
3. takeaway 是最重要的环节
4. 不能为了方法论而方法论

**进一步反馈**：
- "当 Deep Research 拿回的信息过多时，一定要考虑信息的密度和质量"
- "碰一下小助理案例不应保留——按渐进式披露设计"
- "pd-deep-research 必须独立，内部不引用任何其他 skill"
- "命名全部更新，不出现旧 skill 名避免调用失败"

## 2026-05-03：设计决策

### 方案选择：融合重写 vs 吸收

评估了两个方案：
- **方案一（吸收）**：deep-research 加一个"研究模式"——问题：模式切换太晚，Phase 1-3 按主题维度组织信息，到 Phase 4 才切成纵/横，信息收集阶段就走偏了
- **方案三（融合重写）**：以横纵双轴为核心框架，把 deep-research 的信息质量机制嵌入——PM 场景下双轴是更自然的分析框架

**选择方案三**。理由：PM 的调研几乎都围绕"研究对象"展开，双轴框架天然适合。

### 关键设计决策

1. **阶段命名从方法论转向决策需求**
   - 旧：锚点发现→深度阅读→交叉验证→框架整合
   - 新：外面怎么样？→到底怎么回事？→所以呢？我们该怎么做？

2. **方法论退为内部实现**
   - 纵轴/横轴/交汇洞察不作为用户可见阶段名
   - 交叉验证不再是独立阶段，嵌入 Phase 2 持续执行

3. **三层分层产出**
   - Layer 1：决策简报（最多 2 页，纯表格）
   - Layer 2：完整分析（15-25 页，叙事+表格提炼）
   - Layer 3：支持数据（原始研究材料）
   - 层间不重复

4. **独立性原则**
   - SKILL.md 不引用任何其他 skill
   - 产出文件使用通用格式
   - 调用方适配逻辑在调用方一侧

5. **命名**：pd-deep-research（用户选择，强调 PM 决策研究）

### 从两个 skill 各取什么

**从 deep-research**：锚点评估、批次阅读、交叉验证、可信度分级、假设追踪、模板驱动
**从 hv-analysis**：双轴框架、竞品场景 A/B/C、叙事写作+反AI味+敢下判断
**新增**：决策简报（takeaway）、机会识别、信息密度规则

## 2026-05-04：开始验证

**验证主题**：线下商户私域运营
**选择理由**：横轴竞品丰富（有赞/微盟/美团/抖音生活服务），纵轴从 CRM→SCRM→私域运营有清晰演变，交汇点可能揭示"支付场景切入私域"的独特机会

## 2026-05-04：验证完成——线下商户私域运营

**验证结果**：三阶段完整执行，产出四份文件。

### 验证发现摘要

1. **Phase 1（外面怎么样？）**：竞争场景C（5集群20+玩家），核心结构性缺口在"支付切入型"（覆盖广但浅）和"SaaS工具型"（深度够但贵）之间——1.2亿个体户被双重忽视。5个初始假设提出。

2. **Phase 2（到底怎么回事？）**：5个假设逐一验证——H1"支付即私域"方向正确但需修正为"支付+AI"组合；H2 AI降运营人力成立但降行业定制成本暂无实证；H3 企微收费不触发迁移，"去中心化"实为"多入口+单终端"；H4 行业差异极大被强验证；H5 全域融合方向正确但落地远。6高/6中/5待验证。

3. **Phase 3（所以呢？）**：核心结论——"支付+AI"是打开小微商户私域的关键组合，但必须从单一垂直行业切入（推荐餐饮），在微信生态内做增强层而非替代。

### 方法论验证

- **信息密度**：Layer 1 决策简报2页内包含5个关键决策+4个机会窗口+5个关键风险+5个待验证问题，信息密度显著高于旧版
- **决策导向**：每个发现都标注了对决策的影响，不再是"收集了多少信息"而是"改变了什么决策"
- **可信度标注**：6高/6中/5待验证，明确区分已验证事实和待验证假设
- **交汇洞察**：4条纵横交叉洞察是Phase 2最有价值的部分——单纯纵向或横向分析无法得出

### 待改进

- Phase 1 信息源数量偏多（16+），部分来源为二手分析，一手来源（商户访谈、产品实测）不足
- Phase 2 假设验证依赖公开信息，缺少商户侧一手调研数据
- 竞品深度对比中的"用户口碑（正面/负面）"部分数据不够充分，需要更多真实用户评价

## 2026-05-04：Round 2——产出结构重构

**触发**：用户反馈"4个MD文件阅读体验差"。

**核心洞察**：按信息密度组织产出 ≠ 按消费场景组织产出。PM 不是按"我要看高密度信息"来读报告，而是按"我要做决策/汇报/讨论/存档"。生产结构和交付结构应该分离。

**设计决策**：
1. 生产侧：四文件 → 单文档 `research-report.md`（三个分层章节）
2. 交付侧：Phase 3 完成后询问消费场景（快速决策/向上汇报/团队讨论/完整存档）+ 格式（MD/HTML）
3. 消费场景选择时机选 A（Phase 3 后），因为 PM 研究前往往不知道需要什么深度
4. 被其他 skill 调用时：不询问消费场景，直接产出完整文档

**新增模板**：`templates/research-report.md`（统一模板，替代4个独立模板）

**旧模板保留**：01-landscape.md / 02-deep-analysis.md / 03-decision-brief.md / competitive-analysis.md 保留作为内部参考，不再作为最终产出模板

### 订阅支付流失挽回（新主题验证）

**触发**：用户提出新研究主题——商家代扣/订阅套餐的支付流失挽回。

**验证结果**：三阶段完整执行，产出单文档 `research-report.md`。

**核心发现**：
1. 监管三次升级（2021/2024/2026）正在把暗黑模式ROI压到零——"合规+精准挽回"是唯一可持续方向
2. 支付宝代扣解约有三种方式，用户可在支付宝内直接取消，商家通过回调感知——但大多数商家收到回调后只做状态更新不做挽留
3. 非自愿流失（扣款失败）占20-40%，需要"帮付成功"而非"说服留下"
4. 降级/暂停比折扣更可持续——降级是长期价格匹配，折扣是一次性补贴
5. 支付宝有机会从"被动扣款通道"升级为"订阅生命周期管理平台"

**方法论验证**：
- 竞品场景C处理得当：四类聚类（暗黑模式型/合规+折扣型/合规+分层型/无作为型）清晰
- 纵轴叙事流畅：三次监管升级→暗黑模式ROI归零的逻辑链完整
- 交汇洞察有效：监管收紧×支付宝回调机制="合规+解约回调触发的即时推送"机会
- 信息密度通过so-what测试：每个段落都对"挽回策略怎么做"有直接影响

**置信度分布**：5 高 / 6 中 / 5 待验证

## 2026-05-06～05-07：HTML 产出优化 + ai-native-pd 联动修复 + 集成测试

### HTML 产出样式优化

**触发**：用户反馈 HTML 报告大段文字难以抓住重点，需要提升阅读质感。

**改动**：
1. 间距优化：参照 Notion/Substack 长文阅读风格，大幅增加 body padding（80→120px）、h2 上间距（64→80px）、表格单元格 padding（12px 16px→14px 18px）等
2. 列宽收窄：max-width 从 880px 收窄到 780px，更接近长文阅读舒适宽度
3. 机会/风险行高亮改为 hover 触发：移除默认背景色，改为 `.opportunity:hover td` / `.risk:hover td`
4. 有序列表序号修复：`h4 + ol` 的 `counter-reset: none` 改为 `counter-reset: item`，修复所有序号显示为 1 的问题
5. 表格列宽与换行全面修复（见下方）

**表格布局方案（最终版）**：

经过 5 轮迭代，确立以下标准方案：

- 全局 `table-layout: auto`（浏览器根据内容自动分配列宽）
- `th { white-space: nowrap }`（表头不换行，保证收缩列最小宽度）
- `td { overflow-wrap: break-word; word-break: break-word }`（长文本强制换行）
- `.decision-table` 保留 `table-layout: fixed` + 显式列宽百分比（13%/27%/9%/51%）
- JS colgroup 脚本：扫描单元格内容长度，只对短值列（maxCellLen ≤ 8，如置信度/可能性/影响度/优先级/序号）设 `width: 1%` 收缩，其余列由 auto 布局决定
- **关键教训**：表头长度不是列宽的可靠指标——"模式""发现""洞察"等 2 字表头但内容是整段话，用 `width: 1%` 会压成极窄列。必须扫描单元格内容长度来判断

## 2026-05-07：方法论改进——6 项结构性优化

**触发**：完成三案例对比评估后，识别出 6 项系统性弱点，逐一修复。

### 改动清单

1. **搜索策略规范**（SKILL.md）：新增"搜索策略"小节，定义三轮搜索（广度扫描→锚点精读→补缺验证）、总搜索上限 15 次、查询构造原则、信息充分性客观判据、薄结果回退方案。替换了原来模糊的"信息充分性自检"。

2. **消除层间重复**（SKILL.md + writing-quality-standards.md + research-report.md 模板）：交汇洞察加入"新综合"规则——每条必须是 Layer 1 未出现的新判断，单独看纵轴或横轴都得不出。禁止把机会窗口的证据拆成两列重排。提供正反范例。

3. **窄问题轻量模式**（SKILL.md）：新增"产品功能定位"触发路径和轻量模式执行规范——纵向分析压缩为"关键路径依赖"段落、横向减少竞品聚类增加技术可行性验证、搜索上限降为 10 次、产出可少于 5 个决策。

4. **清理旧模板 + 修复不一致**：
   - 旧模板（01-landscape.md / 02-deep-analysis.md / 03-decision-brief.md / competitive-analysis.md）移入 `templates/_legacy/`
   - `[Medium+]` 标签从 confidence-framework.md 中移除，统一为三级标注（高/中/待验证）

5. **打破置信度配额**（SKILL.md + confidence-framework.md）：明确声明"置信度分布由证据实际强度决定，不预设数量配额"，举例说明不均匀分布是正常的。

**置信度分布**：7 高 / 6 中 / 4 待验证（信息源 16 个，高优先级 4 个）

### 新增发现（相比 Round 2 旧版案例）

1. **设计哲学分析**：每个竞品聚类从"做了什么"深入到"为什么这样做"——暗黑模式的"摩擦力=留存"模型、折扣型的"价格问题=价格方案"线性思维、分层型的"尊重意图+匹配原因"非线性思维
2. **边缘陷阱**：折扣策略的隐藏合规风险——可能被认定为"变相阻拦"
3. **演进方向**：从"流失挽回"到"流失预防"的趋势，预防比挽回成本低5-7倍
4. **推理链结构**：5个决策都按 发现→推断→结论 展开，含"反对意见"段
5. **数据叙事融合**：关键数据嵌入因果句式而非孤立罗列
